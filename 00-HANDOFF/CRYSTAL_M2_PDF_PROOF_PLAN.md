**Branch:** `KIRCH-REPORTS-CRYSTAL-M2-RUNTIME-ENVIRONMENT-CHECKLIST`

**Decision carried forward:** Isolated Windows worker only. No direct Crystal integration into Salryn host.

## 1. Purpose

Define the exact evidence required before Salryn attempts any real SAP Crystal PDF render proof.

This document does not prove rendering. It exists so Crystal-M3 can start from a controlled, auditable plan instead of guessing runtime, licensing, template, output, and safety boundaries.

## 3. Proof architecture

Required proof flow:

```text
Salryn host
  -> generate server-owned dataset envelope
  -> write/send dataset package to isolated worker boundary
  -> worker validates protocol and template allow-list
  -> worker renders PDF using selected Crystal runtime
  -> worker returns artifact metadata only
  -> host records/report displays metadata
```

Forbidden proof flow:

```text
.rpt template -> direct production database query -> duplicated VAT/refund/void/tax formulas
```

## 5. Dataset package proof

Dataset package must be created by Salryn host, not the worker.

Required dataset fields:

- `schemaCode`
- `schemaVersion`
- `reportKind`
- `reportTitle`
- `generatedAt`
- `scope`
- `controlTotals`
- `rows`
- `sourceHashes`
- `safetyFlags`
- `contentSha256`
- `datasetSha256`
- `summary`

Required safety conditions:

- `safetyFlags.datasetAvailable = true`
- `safetyFlags.usesCanonicalM5Projection = true` for official/tax reports
- `safetyFlags.birAccreditationClaimed = false`
- `safetyFlags.eSalesTransmissionEnabled = false`
- `safetyFlags.productionActivationEnabled = false` unless a future authorized branch proves otherwise; M2 does not authorize this.


## 6. Template proof

First proof uses exactly one allow-listed template.

Template must satisfy:

- Template ID is fixed, not caller-supplied.
- Template path is resolved inside worker config, not from request payload.
- Template SHA-256 is recorded before render.
- Template contains no DB credentials.
- Template does not connect directly to the production database.
- Template does not run SQL.
- Template binds to the dataset package only.
- Template does not recompute official tax/refund/void totals.

Template evidence to collect:

```text
Template ID:
Template file name:
Template SHA-256:
Template source/owner:
Approval note:
Data binding mode:
Credential scan result:
```

## 7. Worker self-check plan

Before rendering, the worker must support a self-check command or endpoint.

Self-check should report:

- Worker executable version.
- Worker protocol version.
- Target framework.
- Process bitness.
- OS bitness.
- Crystal runtime detected: yes/no.
- Crystal runtime version.
- Crystal runtime bitness.
- Supported output kinds.
- Configured output root.
- Configured template IDs and hashes.
- Max timeout.
- Max concurrent jobs.
- Last startup error if any.

Self-check must fail closed if:

- Runtime is missing.
- Runtime bitness is unsupported.
- Output root is missing/unwritable.
- Template allow-list is empty.
- Template hash does not match expected config.

## 8. First render proof case

Use one controlled report.

Recommended initial proof:

```text
Report kind: traditional-x-reading or tax-bucket-summary

Range: small known range, <= 1 day
```

## 9. Negative proof cases

Crystal-M3 must prove fail-closed behavior, not only success.

Required negative cases:

1. Runtime missing -> safe `Crystal.RuntimeMissing` or equivalent error.
2. Template ID unknown -> safe allow-list error.
3. Template hash mismatch -> safe integrity error.
4. Output kind not PDF -> safe output-kind error.
5. Dataset hash mismatch -> safe dataset integrity error.
6. Timeout -> safe timeout error and no advertised artifact.
7. Output root unwritable -> safe output error.
8. Attempted caller file path -> rejected by host/worker protocol.
9. Attempted caller SQL -> rejected by host/worker protocol.
10. Attempted caller `.rpt` upload/path -> rejected by host/worker protocol.

## 10. Artifact metadata contract

Every successful proof artifact must record:

```json
{
  "fileName": "...",
  "contentType": "application/pdf",
  "byteLength": 0,
  "sha256": "...",
  "createdAtUtc": "...",
  "rendererName": "SAP Crystal Reports",
  "rendererVersion": "...",
  "workerProtocolVersion": "SALRYN_CRYSTAL_WORKER_V1",
  "sourceDatasetContentSha256": "...",
  "sourceDatasetEnvelopeSha256": "...",
  "templateId": "...",
  "templateSha256": "..."
}
```

No artifact may be accepted without byte length and SHA-256.

## 12. Stop conditions

Stop before coding Crystal-M3 if any are true:

- Runtime support cannot be confirmed for the selected worker target.
- Runtime bitness is 32-bit.
- Worker machine is unsupported Windows or missing Desktop Experience where required.
- Licensing/redistribution is not confirmed by Kirch/project owner.
- Template source is not approved.
- Template includes credentials or direct DB SQL.
- Output folder policy is not approved.
- Proof machine is unavailable.

## 13. M2 conclusion

M2 does not prove Crystal rendering. It defines the readiness gate.

Crystal-M3 may begin only after runtime, licensing, worker target, template, output policy, and proof machine are all confirmed.
