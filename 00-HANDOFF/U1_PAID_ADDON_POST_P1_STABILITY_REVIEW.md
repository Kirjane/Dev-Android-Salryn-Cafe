## Stability checks

### AR report disclosure

Verdict: **Closed in source and focused runtime proof.**

- `/api/owner-reports/summary` first requires `Reports.View` and the base `Reports` feature.
- The optional AR section is included only when `ReceivablesUtangLedger` is allowed **and** `Receivables.View` is present.
- A report-only user still receives the non-AR report, but `Receivables` is `null`.
- A user with both `Reports.View` and `Receivables.View` receives the AR section when U1 is licensed.
- The focused U1 runtime smoke exercised both negative and positive cases and passed.

### Collection reversal operator usability

Verdict: **Code-complete for an authorized operator; visual/manual proof pending.**

- The React ledger exposes a Reverse action only when the session contains `Receivables.Adjust`.
- The operator must select an original collection, enter a nonblank reason, and explicitly check a confirmation statement.
- The confirmation statement explains that the original entry remains and an append-only reversal restores the balance.
- The reversal button and cancellation controls are locked while the request is pending.
- On success, summary, customer balances, and the selected ledger are invalidated/refetched.
- The UI detects a matching `CollectionReversal` by `collectionId` and disables the original collection's action as `Reversed`.
- The API independently requires U1 plus `Receivables.Adjust`; frontend manipulation cannot bypass it.
- Admin receives `Receivables.Adjust` by default. Manager does not. Therefore the feature is operator-usable by Admin or a custom authorized role, not by the default Manager role.

Usability limitations requiring scope decisions:

- Ledger entry types are rendered as numeric enum values. The Reverse action works because it uses the matching numeric contract, but human-readable labels would reduce operator confusion.
- A stale/direct second reversal normally returns `Receivables.CollectionNotFound` because only active collections are selected. A concurrent race can return `Receivables.CollectionAlreadyVoided`. Both deny mutation, but a single explicit already-reversed message would be clearer.
- This review did not open a browser or visually confirm responsive layout, focus behavior, error tone, or button visibility.

### Duplicate reversal

Verdict: **Denied and mutation-safe.**

- The service reads only an active, non-voided collection.
- The state update repeats the `voided_at IS NULL` predicate.
- An update race that affects anything other than one row returns a conflict and does not append another reversal.
- The transaction appends one `CollectionReversal` entry only after the active-row update succeeds.
- Existing uniqueness protection and the transaction prevent a second reversal entry for the same collection.
- Focused runtime proof reverses once, retries, requires failure, and verifies exactly two ledger records for that collection: the original Collection and one CollectionReversal.

### Base and paid entitlement behavior

Verdict: **Fail-closed in automated proof.**

- Base Host features do not include `ReceivablesUtangLedger`.
- Base Host requests to U1 APIs return the feature-not-licensed denial.
- Cash checkout remains governed by the base `Pos` feature and does not require U1.
- Full Utang and Cash + Utang detect the `AccountsReceivable` payment method and require U1 plus `Receivables.CreateCreditSale`.
- All customer, summary, ledger, collection, adjustment, and reversal endpoints use the common U1 license guard plus their operation-specific permission.
- A paid Host license does not override missing user permissions.
- Unknown or malformed feature keys remain rejected before signing or during verification.

### Default roles and Terminal boundary

Verdict: **Closed in source and focused runtime proof.**

- Default Cashier has base sales permissions but no Receivables permissions.
- Licensed Cashier credit checkout without `Receivables.CreateCreditSale` is rejected.
- Default Manager can view receivables, create credit sales, collect, and manage customers, but cannot adjust/reverse.
- Default Admin has the full U1 permission set, including adjustment/reversal.
- Requests carrying Terminal context are rejected by the local-only receivables boundary.
- Terminal licensing cannot unlock the Host-only U1 feature.
- No receivables route was added to the Terminal shell.

- The documented boundary says it is an operational receivables tracker, not an accounting compliance system, BIR registration feature, official accounting module, or tax-reporting module.
- The P1 repair introduced no BIR, accounting-compliance, official-accounting, or tax-reporting claim in runtime UI or API output.
